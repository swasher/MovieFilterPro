# UI Principles

Ниже зафиксированы рабочие визуальные правила для нового Svelte UI. Это не большой дизайн-гайд, а короткий набор решений, которые уже проверены на живых экранах и должны использоваться дальше консистентно.

## Смысловые роли

- `badge` использовать только для статуса, редкого сигнала состояния или служебного маркера.
- `chip` использовать только для фильтра, тега или вторичного перечисления.
- ключевые атрибуты сущности показывать через `facts row` или `label/value`, а не через облако badge.
- техническую информацию всегда уводить в secondary zone и не смешивать с основным маршрутом чтения.
- одинаковая визуальная форма должна означать одинаковую функцию.

## Маршрут чтения

У каждой detail-страницы должен быть явный порядок:

1. Название сущности
2. Ключевые факты
3. Основные пользовательские действия
4. Основное описание
5. Вторичные детали и связанные сущности
6. Служебные данные и maintenance actions

Если все блоки выглядят одинаково важными, экран начинает читаться как CMS, а не как пользовательская карточка сущности.

## Паттерны

### Hero

- крупный title
- optional subtitle/original title
- одна строка или компактная сетка ключевых фактов
- один статусный ряд

### Facts

- ключевые reference facts показываются текстом
- у фактов должно быть постоянное место
- формат `2025 • Film • 105 min • 16+` предпочтительнее хаотичного набора badge

### Primary Actions

- действия пользователя должны читаться быстрее, чем служебные кнопки
- mutually exclusive статусы лучше воспринимаются как segmented row или крупные pill-buttons
- rating должен иметь явное числовое значение, а не только декоративные звезды

### Secondary Meta

- технические данные, sync, source, ids и maintenance controls держать отдельно
- они не должны спорить с основным контентом по контрасту и визуальному весу

### Related Content

- связанные люди, фильмы и списки оформлять легкими карточками без тяжелых рамок
- если элемент не является действием, не надо визуально делать его похожим на control

## Практические правила

- если информация помогает принять пользовательское решение, она должна быть ближе к title и иметь больший визуальный вес
- если информация нужна редко или для поддержки данных, она должна жить ниже или слабее
- не превращать весь экран в набор `Card` внутри `Card`
- не использовать badge как универсальную форму для любых данных
- пустое пространство использовать для иерархии, а не для “воздуха ради воздуха”

## Текущий scope

Эти принципы уже применены к `/kinozal` и являются базой для Vault detail-экранов:

- movie detail
- person/actor detail
