# Кеширование изображений Vault

> Живой документ: при изменении URL-контракта, endpoint-а или стратегии
> кеширования обновляйте его.

## 1. Зачем это нужно

Раньше `vault` отдавал в API прямые ссылки на `image.tmdb.org`, и браузер
качал постеры, бэкдропы и фотографии персон напрямую с внешнего CDN. Из-за
этого:

- доступность изображений зависела от сети и политик TMDB;
- при каждом открытии списка часть картинок загружалась заново;
- нельзя было централизованно управлять размерами и заглушками.

Теперь по умолчанию браузер обращается к внутреннему endpoint Django:
скачивание, проверка ответа и хранение файла выполняются на сервере. При этом
холодный кеш **не блокирует** запрос: endpoint сразу отдаёт временный редирект
на CDN TMDB, а файл докачивает в фоне (см. §6).

Есть и глобальный тумблер, который полностью выключает дисковый кеш и
возвращает прямые CDN-URL (см. §7).

## 2. Слои

```text
Модель / API-сериализатор
    │  ImageService.url(raw_path, size, kind)
    ▼
/api/vault/images/{kind}/{size}/{path}
    │  ImageService.serve(...)
    ▼
ImageService → ImageCache
    │
    ├── файл есть ─────────────► StreamingHttpResponse (200, чанками)
    ├── 404/410 от TMDB ───────► маркер .missing, 200 + SVG-заглушка
    ├── сеть/5xx/не image ─────► маркер .failed, 302 на CDN
    └── файла нет ─────────────► 302 на CDN + фоновая загрузка
```

Если глобальный тумблер выключен, `ImageService.url()` вообще не ведёт на
endpoint — модели и сериализаторы получают прямой URL CDN.

Ключевой принцип: **приложение не знает про кеш**. Модели и сериализаторы
вызывают только `ImageService.url()`; очистка `cache/vault/` не требует
изменений в коде и не ломает URL.

## 3. Центральная функция

`vault/services/image_service.py`:

```python
ImageService.url(raw_path, size="w500", kind="poster")
```

- `raw_path` — относительный путь TMDB (`/abc.jpg`), полный URL TMDB или уже
  готовый локальный URL;
- `size` — один из разрешённых размеров TMDB (`w185`, `w342`, `w500`, `w780`,
  `w1280`, `original` и т.д.);
- `kind` — `poster`, `backdrop` или `profile`; влияет на каталог кеша и
  заглушку.

Все места, которые раньше собирали URL на `image.tmdb.org`, теперь используют
эту функцию: `Movie.poster_url`, `Person.photo_url`, `Collection.poster_url`,
кандидаты TMDB-поиска, галерея фото персоны и т.п.

### Размеры под контекст

Каждый размер — это отдельный файл дискового кеша, поэтому размер выбирается
в API-сериализаторе под место интерфейса, а не «на всякий случай» `w500`:

| Контекст | Размер | Константа |
| --- | --- | --- |
| Карточки фильмов, фильмография, сезоны, коллекции, кандидаты TMDB | `w342` | `POSTER_CARD_SIZE` |
| Постер на странице фильма | `w500` | `POSTER_DETAIL_SIZE` |
| Карточки персон, состав и съёмочная группа на странице фильма | `w185` | `PROFILE_CARD_SIZE` |
| Главное фото на странице персоны, галерея (крупно) | `w500` | `PROFILE_DETAIL_SIZE` |
| Зум (постер/фото) | `original` | — |
| Бэкдроп коллекции в карточке | `w780` | `BACKDROP_CARD_SIZE` |
| Бэкдроп на странице фильма | `w1280` | `BACKDROP_DETAIL_SIZE` |

Свойства моделей `Movie.poster_url` / `Person.photo_url` остаются
«деталевыми» (`w500`): сериализаторы списков явно вызывают
`get_poster_url(...)` / `get_photo_url(...)` с карточным размером. Фронтенд
размеры не подставляет — он рендерит то, что вернул API.

Чужие абсолютные URL (например, пользовательская обложка с другого хостинга)
не проксируются и возвращаются как есть. Это осознанный компромисс: endpoint
не должен превращаться в открытый прокси.

## 4. Endpoint

```text
GET /api/vault/images/{kind}/{size}/{path}
```

Требует аутентификации. Возможные ответы:

| Ситуация | Ответ | Заголовки |
| --- | --- | --- |
| Файл в кеше | `200` + `StreamingHttpResponse` (чанки по 64 КБ) | `Cache-Control: private, max-age=31536000, immutable`, `ETag`, `Content-Length` |
| Файла нет (холодный кеш) | `302` на `TMDB_IMAGE_BASE_URL/<size>/<path>` + фоновая загрузка | `Cache-Control: no-store` |
| Изображения нет в источнике | `200` + SVG-заглушка (файл из `static/img/`) | `Cache-Control: private, max-age=3600`, `Content-Length` |
| Недавняя ошибка (`.failed`) | `302` на CDN (браузер может попробовать сам) | `Cache-Control: no-store` |
| Некорректный kind/size/path | `404` | — |
| Нет сессии | `401` | — |

Долгий `max-age` безопасен: путь TMDB иммутабелен, один и тот же URL всегда
отдаёт один и тот же файл. `no-store` на редиректах нужен, чтобы после
прогрева кеша браузер не продолжал ходить по старому промежуточному ответу.

Заглушка отдаётся сразу (`200`), а не редиректом на `/static/...`: редирект
стоил лишнего round-trip на каждую картинку, которой нет в источнике, и при
этом всё равно не кешировался (`no-store`). Час кеша — компромисс: браузер не
дёргает endpoint на каждом рендере, но если источник позже начнёт отдавать
файл, подхватит его в пределах часа. Если файл заглушки не найден (например,
не выполнен `collectstatic`), endpoint откатывается на прежний редирект.

`private` (а не `public`) выбран осознанно: endpoint требует сессию, а общего
reverse-proxy кеша в деплое нет. Браузерный кеш `private` не ограничивает —
год `immutable` работает как раньше.

## 5. Кеш на диске

```text
CACHE_ROOT/
└── vault/
    ├── poster/
    │   ├── w342/
    │   └── w500/
    ├── backdrop/
    │   └── w1280/
    └── profile/
        ├── w185/
        └── w500/
```

Имя файла: `sha256(image_path)` + расширение источника. Каталог уже содержит
kind и size, поэтому один и тот же путь в разных размерах не конфликтует.

Рядом с файлом могут лежать маркеры:

| Маркер | Когда создаётся | TTL |
| --- | --- | --- |
| `<file>.missing` | TMDB ответил `404`/`410` | 24 часа |
| `<file>.failed` | сеть, таймаут, `5xx`, не-image ответ | 30 секунд |

Механика повторяет `moviefilter/image_caching.py`:

- загрузка во временный файл в том же каталоге;
- публикация через `os.replace` (читатель не увидит частичный файл);
- single-flight на процесс: параллельные запросы одного изображения ждут одну
  загрузку; локи для этого — фиксированный набор полос (`LOCK_STRIPES`), а не
  словарь на каждый ключ, поэтому память не растёт с числом картинок;
- скачивание чанками по 64 КБ (`DOWNLOAD_CHUNK_SIZE`), чтобы не делать сотни
  итераций на `original` в несколько МБ;
- проверка `Content-Type` (`image/*`) и лимит размера (32 МБ).

Фоновые загрузки идут через общий пул (8 потоков). Потоки живут долго, поэтому
thread-local `requests.Session` — одна на поток процесса, общая для всех
`ImageCache` (kind/size), — переиспользует TCP/TLS-соединения к TMDB между
картинками. Иначе каждая пара kind/size держала бы свою сессию на каждый
воркер и платила отдельный TLS-handshake.

Горячий файл отдаётся `StreamingHttpResponse` с async-итератором: чанки по
64 КБ читаются в `asyncio.to_thread`. Так ASGI не материализует файл целиком
в память — `FileResponse` с sync-итератором под ASGI делает именно это через
`sync_to_async(list)(...)`, что для `original` на несколько МБ даёт лишний пик
памяти и задержку. `Content-Length` выставляется явно, поэтому браузер видит
размер и прогресс.

Сам модуль Kinozal не переиспользуется напрямую: он связан с `MovieRSS`,
`movie_pk`, приоритетами и fastpic. В `vault/services/image_cache.py` вынесена
только общая, независимая от источника механика.

## 6. Холодный кеш: 302 на CDN + фоновая загрузка

`ImageCache.get_or_schedule()` не скачивает файл в запросе:

- файл есть → `200` + стриминг файла чанками;
- `404/410` → маркер `.missing` + заглушка;
- иначе → загрузка ставится в общий пул (8 потоков), а клиент сразу получает
  `302` на CDN TMDB с `Cache-Control: no-store`.

Зачем: первая загрузка страницы не ждёт сеть — картинки параллельно тянет
браузер (HTTP/2, много потоков), а сервер в это время прогревает локальный
кеш. Плата — на холодном кеше файл кратковременно качается дважды (браузер +
сервер). Загрузки дедуплицируются в процессе (single-flight), поэтому
повторные запросы не плодят задачи.

После прогрева тот же URL отдаёт `200` с `immutable`, и браузер кеширует его
на год — «медленная» только первая загрузка.

## 7. Глобальный тумблер кеширования

`moviefilter.UserPreferences.vault_image_cache_enabled` (по умолчанию `True`),
переключатель — в Preferences → «Изображения».

Когда выключен, `ImageService.url()` возвращает прямой URL CDN
(`TMDB_IMAGE_BASE_URL/<size>/<path>`): endpoint не используется, работает
только браузерный кеш. Это режим для сравнения/отладки, а не для продакшна.
Значение кешируется в `ImageService` на 5 секунд и сбрасывается при сохранении
Preferences.

## 8. Фото персон и фронтенд

- `GET /api/vault/persons/{id}/images` отдаёт список фото из TMDB. Список
  `file_path` кешируется в LocMem **без TTL** (`vault/services/person_images_service.py`);
  пустой список тоже кешируется, ошибки — нет.
- `TmdbRateLimiter` для этого вызова намеренно не используется: это одиночное
  интерактивное чтение, которое выполняется один раз на персону за жизнь
  процесса. Лимитер нужен пакетным операциям, а sync и так живёт в отдельном
  HUEY-процессе.
- `+page.ts` страницы персоны запрашивает данные и фото **параллельно**
  (таймаут фото — 5 с), поэтому фото не стартуют после рендера страницы.
  Бонус: префетч по hover на карточке персоны тянет и фото.
- В сетке «Фото персоны» используется `thumb_url` (`w185`); `w500`/`original`
  остаются для зума. Карточки персон (`PersonCard`: каст на странице фильма,
  список персон, блоки на главной) тоже получают `w185` (`PROFILE_CARD_SIZE`),
  а крупное фото на странице персоны — `w500` (`PROFILE_DETAIL_SIZE`).
- `VaultImage.svelte` — общий компонент для всех картинок Vault: muted-подложка
  со спиннером (появляется с задержкой 150 мс, чтобы закешированные картинки
  не мигали) и плавное скрытие после `onload`. Работает и как обычный `<img>`,
  и как `ImageZoom.Trigger`.

## 9. Безопасность

- Источник всегда собирается из `TMDB_IMAGE_BASE_URL`; endpoint не принимает
  произвольный URL.
- `size` ограничен allowlist-ом.
- `path` проверяется регуляркой, запрещены `..`, `.`, пустые сегменты,
  backslash, пробелы и слишком длинные значения.
- Ответ источника обязан иметь `Content-Type: image/*`.
- Файлы кеша имеют только безопасные расширения изображений.
- Endpoint требует аутентифицированного пользователя.

## 10. Очистка

Кеш можно удалить целиком:

```bash
rm -rf cache/vault
```

или в Docker:

```bash
docker exec <container> rm -rf /app/cache/vault
```

После этого изображения скачаются заново при следующем открытии страниц.
`media/` не затрагивается.
