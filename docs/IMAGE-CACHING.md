# Кеширование постеров Kinozal (image cache)

> **Назначение:** этот документ описывает, как кеш постеров Kinozal устроен
> **сейчас**. Это живой документ: при изменении логики загрузки, состояний кеша
> или endpoint-а обновляйте его.
>
> История решения и мотивация переделки — в корневом
> [`PLAN-IMAGE-CACHE-REFACTORING.md`](../PLAN-IMAGE-CACHE-REFACTORING.md).

## 1. Что решает кеш

Раньше браузер загружал постер напрямую с внешнего хостинга (`fastpic.org`,
`imgbox.com`, `imageban.ru`, `kinozal.tv` и т.п.). Из-за этого:

- доступность постера зависела от сети конкретного устройства;
- источник мог отдавать заглушку или `404`, и постер «пропадал»;
- после повторной загрузки списка браузер мог показать то внешний URL, то
  локальный файл, то SVG-заглушку;
- нельзя было централизованно обойти антихотлинк-защиту источников.

Сейчас браузер **не знает внешний URL постера**. Он всегда запрашивает внутренний
endpoint Django, а скачивание и кеширование выполняет сервер.

## 2. Поток данных

```text
Скан Kinozal
    │
    ▼
MovieRSS.poster = внешний URL постера
    │
    ▼
GET /api/kinozal/movies
    │  poster_url = /api/kinozal/movies/<id>/poster
    ▼
Браузер: <img src="/api/kinozal/movies/<id>/poster">
    │
    ▼
GET /api/kinozal/movies/<id>/poster
    │
    ├── кеш готов  ──────────────────────────────► 200 + файл из cache/
    │
    ├── кеша нет / загрузка идёт / была ошибка ──► 503 no-store
    │                                              │
    │                                              └── фронтенд повторяет запрос
    │
    └── активен .missing ────────────────────────► 302 на /static/img/poster-placeholder.svg
```

Скачивание выполняется **в фоновом потоке** внутри Django-процесса. HTTP-ответ
на постер не ждёт загрузки: он сразу сообщает `pending` (`503`), а фронтенд
повторяет запрос. Когда файл готов, очередной повтор получает `200`.

## 3. Где и как хранится кеш

### 3.1. Каталог и имена файлов

Настройки в `movie_filter_pro/settings.py`:

```python
# MEDIA — постоянные пользовательские данные (кастомные обложки и т.п.)
MEDIA_ROOT = BASE_DIR / 'media'
MEDIA_URL = '/media/'

# CACHE — временные производные данные (кеш постеров)
CACHE_ROOT = BASE_DIR / 'cache'
CACHE_URL = '/cache/'
```

`CACHE_ROOT` больше не вложен в `MEDIA_ROOT`: это намеренно разные жизненные
циклы. `media/` — пользовательские данные, которые нельзя терять; `cache/` —
временный кеш, который можно удалить и который пересоздастся сам.

В Docker это две отдельные точки монтирования:

```text
/app/media  → постоянный volume (кастомные обложки и другие пользовательские файлы)
/app/cache  → временный volume (кеш постеров; можно очищать)
```

Файл кеша строится в `moviefilter/image_caching.py::_build_cached_paths`:

```text
{movie_pk}_{sha256(image_url)}{extension}
```

- `movie_pk` — ID записи `MovieRSS`;
- `sha256(image_url)` — хеш **оригинального** URL (до подмены зеркала);
- `extension` — расширение из последнего сегмента URL (`.jpg`, `.jpeg`, `.png`…),
  иначе `.jpg`.

Пример:

```text
cache/10654_0f32c5f3c52a0f180682d1ee23bdaaaba718a2172aa301ec4be25461f0999f6d.jpg
```

ID фильма в имени нужен потому, что один и тот же URL может встречаться у разных
записей `MovieRSS`. Это же имя используется для поиска файлов при очистке.

`CACHE_URL` сейчас нужен только legacy-хелперу `get_cached_image_url`; новый
endpoint отдаёт файл потоком (`FileResponse`) и `CACHE_URL` не использует.
В `DEBUG` этот префикс обслуживается через `static()` в `movie_filter_pro/urls.py`,
чтобы legacy-хелпер продолжал работать локально.

### 3.2. Маркеры состояний

Рядом с файлом кеша лежат служебные файлы-маркеры:

| Маркер | Когда создаётся | Время жизни | Что означает |
| --- | --- | --- | --- |
| `<file>.missing` | источник ответил `404`/`410` | 24 часа | Постер отсутствует, временно показываем заглушку |
| `<file>.failed` | сеть/таймаут/`5xx`/непредвиденная ошибка | 30 секунд | Временная ошибка загрузки, нужно повторить позже |

Особенности:

- `.missing` содержит версию формата (`MISSING_MARKER_VERSION = "2"`).
  Маркеры без версии (пустые файлы, созданные старым загрузчиком) считаются
  устаревшими: удаляются и не блокируют повторную загрузку.
- `.missing` истекает через 24 часа. Если источник позже восстановит URL,
  постер появится после следующего обращения.
- `.failed` даёт быстрый повтор: через 30 секунд маркер перестаёт учитываться.
- Оба маркера проверяются в `_has_active_missing_marker` / блоке проверки
  `.failed` внутри `get_cached_image_state`.

### 3.3. Атомарная запись

Загрузчик не пишет сразу в итоговый файл:

1. создаёт временный файл в том же каталоге кеша
   (`.<cached_filename>.<random>.tmp`);
2. полностью записывает в него ответ источника;
3. публикует файл через `os.replace(tmp, cached)`.

Это гарантирует, что endpoint никогда не увидит частично записанный файл.
Временный файл удаляется в `finally`, если загрузка упала.

## 4. Состояния кеша и endpoint

### 4.1. Состояния

Состояния возвращает `get_cached_image_state(image_url, movie_pk, priority)`:

| Состояние | Условие |
| --- | --- |
| `CACHE_STATUS_READY` | итоговый файл существует |
| `CACHE_STATUS_MISSING` | URL пустой **или** активен валидный `.missing` |
| `CACHE_STATUS_PENDING` | свежий `.failed`, загрузка уже идёт или только что запущена |

Логика `get_cached_image_state`:

1. если `image_url` пустой → `MISSING`;
2. если файл кеша существует → `READY`;
3. если `.missing` валиден (текущая версия и моложе 24 часов) → `MISSING`;
4. если `.failed` моложе 30 секунд → `PENDING` без запуска нового потока;
5. иначе запускает `download_and_cache_image` в daemon-потоке (если для пары
   `(movie_pk, image_url)` загрузка ещё не идёт) и возвращает `PENDING`.

Параметр `priority` в этой функции сейчас не используется: endpoint кеширует
постеры независимо от приоритета. Старое ограничение `VALID_PRIORITY`
(`HIGH`, `LOW`, `DEFER`) осталось только в legacy-хелпере
`get_cached_image_url`; сам хелпер сейчас не вызывается из API/UI и оставлен
для совместимости и тестов.

### 4.2. Endpoint постера

`moviefilter/api.py`:

```text
GET /api/kinozal/movies/{movie_id}/poster
```

Требует аутентифицированного пользователя (`401` без сессии), ищет `MovieRSS`
по `pk` (`404`, если записи нет) и возвращает:

| Ситуация | Ответ | Заголовки |
| --- | --- | --- |
| Кеш готов | `200` + `FileResponse` | `Content-Type` по расширению, `Cache-Control: private, max-age=86400` |
| Загрузка идёт / временная ошибка | `503` | `Cache-Control: no-store`, `Retry-After: 1` |
| Постер отсутствует | `302` на `/static/img/poster-placeholder.svg` | `Cache-Control: no-store` |
| Файл исчез между проверкой и отдачей | `503` | `Cache-Control: no-store`, `Retry-After: 1` |

`Content-Type` определяется через `mimetypes.guess_type`; если расширения нет
или оно неизвестно, используется `image/jpeg`.

`Cache-Control: no-store` на `302` и `503` важен: браузер не должен запомнить
промежуточное состояние и продолжать показывать заглушку после того, как
постер уже скачан.

### 4.3. Список фильмов

`GET /api/kinozal/movies` больше не отдаёт внешний URL. В поле `poster_url`
всегда лежит внутренний адрес:

```json
{
  "id": 10654,
  "poster_url": "/api/kinozal/movies/10654/poster"
}
```

Поэтому браузер физически не может обратиться к внешнему хостингу напрямую.
В dev-режиме Vite проксирует `/api` на Django (`front/vite.config.ts`).
В production `/api` должен направляться на Django так же, как остальные API.

## 5. Загрузчик

Основная функция — `moviefilter/image_caching.py::download_and_cache_image`.

### 5.1. HTTP-сессия

На каждую загрузку создаётся `requests.Session`:

- `User-Agent` — браузерный (`IMAGE_REQUEST_USER_AGENT`), не `python-requests`;
- `HTTPAdapter` с `Retry`:
  - `total=3`;
  - `backoff_factor=1`;
  - повтор для `429`, `500`, `502`, `503`, `504`;
- таймауты: `connect=10s`, `read=30s`.

Браузерный `User-Agent` обязателен для некоторых источников: например, fastpic
отвечает `404` на `python-requests`, даже если cookie уже получены.

### 5.2. Защита от параллельных загрузок

Глобальный словарь:

```python
downloading_images: dict[tuple[int, str], bool]
```

Ключ — `(movie_pk, original_image_url)`, доступ защищён
`downloading_images_lock`.

- `get_cached_image_state` не запускает новый поток, если ключ уже есть;
- `download_and_cache_image` повторно проверяет ключ под блокировкой (защита от
  гонки между проверкой и стартом потока);
- в `finally` ключ удаляется.

Ограничение: словарь живёт в памяти процесса. Если Django запущен в несколько
worker-ов, каждый worker имеет свой словарь, и один и тот же постер может
скачиваться дважды. Это безопасно: публикация идёт через `os.replace`, а
итоговый файл просто перезаписывается атомарно.

### 5.3. Обработка ошибок

| Ошибка | Результат |
| --- | --- |
| `HTTP 404` / `410` | `.missing` (заглушка на 24 часа) |
| Другой `HTTP` (`403`, `5xx`…) | `.failed` |
| `ConnectTimeout`, `ReadTimeout` | `.failed` |
| `RequestException` (сеть, TLS и т.п.) | `.failed` |
| Успешная загрузка | файл публикуется, `.failed` удаляется |

Успешная загрузка также удаляет старый `.missing`, если он почему-то остался.

### 5.4. Особый случай fastpic

Fastpic требует два условия для прямой ссылки на файл:

1. cookie `fp_n_uid`, которую ставит `https://fastpic.org/`;
2. браузерный `User-Agent`.

Без cookie или с `python-requests` direct URL отвечает `404`, хотя страница
`https://fastpic.org/view/...` открывается. Поэтому в загрузчике есть отдельная
ветка:

```text
_is_fastpic_url(url)
        │
        ▼
_ensure_fastpic_cookies(session)
        │  cookie ещё нет?
        ▼
_prime_fastpic_session(session)  GET https://fastpic.org/
        │  cookie из ответа кешируются в _fastpic_cookies
        ▼
GET image_url
        │
        ├── 200 ──────────────────────────────► сохранить файл
        │
        └── 403/404 ──► _refresh_fastpic_cookies()
                              │
                              ▼
                        повторный GET image_url
                              │
                              ├── 200 ────────► сохранить файл
                              │
                              └── 403/404/410
                                      │
                                      ├── cookie получены ──► .missing
                                      └── cookie нет ───────► .failed
```

Детали:

- `_is_fastpic_url` распознаёт `fastpic.org` и любые `*.fastpic.org`;
- `_fastpic_cookies` — процессный кеш cookie; `_fastpic_prime_lock` не даёт
  несколько потоков одновременно получать cookie;
- cookie применяются к сессии с доменом `.fastpic.org`, поэтому подходят для
  `i122.fastpic.org`, `i126.fastpic.org` и т.п.;
- если cookie получить не удалось, `403/404/410` **не** превращается в
  `.missing`: выбрасывается `RequestException`, и ставится `.failed`. Иначе
  временная антибот-блокировка навсегда «хоронила» бы существующий постер;
- обновление cookie выполняется один раз на запрос. Если после успешного
  обновления источник снова отдал `404`, это уже считается отсутствием постера;
  если обновить cookie не удалось — это временная ошибка (`.failed`).

### 5.5. Зеркала источников

Перед загрузкой URL проходит через `resolve_mirror_url`:

```python
SOURCE_MIRRORS = {
    "kinozal.tv": "kinozal.guru",
}
```

Домен из `SOURCE_MIRRORS` заменяется на рабочее зеркало. Хеш и имя файла кеша
при этом считаются от **оригинального** URL, чтобы файл не «переезжал» при
смене зеркала.

## 6. Frontend

Компонент: `front/src/lib/components/KinozalPoster.svelte`.

Что он делает:

- лениво загружает постер через `IntersectionObserver` (`rootMargin: 300px`);
- показывает `Skeleton`, пока изображение не загрузилось;
- при `onerror` повторяет запрос с задержками **1, 2, 5, 10, 15 секунд**;
- к повторному URL добавляет `?retry=N`, чтобы браузер не взял промежуточный
  ответ из HTTP-кеша;
- после исчерпания попыток показывает текстовый fallback (`no poster`);
- при изменении `src` сбрасывает состояние и счётчик повторов;
- очищает таймер при размонтировании.

Важно: `503` от endpoint-а — это невалидный ответ для `<img>`, поэтому браузер
вызывает `onerror`, и компонент повторяет запрос. `302` на SVG-заглушку —
наоборот, успешная загрузка: заглушка считается финальным состоянием и
повторов не вызывает.

## 7. Очистка кеша

Функция `remove_cached_image(movie_pk)`:

- удаляет все файлы, начинающиеся с `{movie_pk}_`;
- удаляет их `.missing` и `.failed` маркеры;
- удаляет ключи `(movie_pk, url)` из `downloading_images`.

Вызывается при действиях, после которых постер больше не нужен:

- `hide` (SKIP);
- `delete`;
- `vault-will-watch` (SKIP);
- `wait-trans`.

`defer` кеш не удаляет.

Автоматической очистки по возрасту или размеру нет. При необходимости каталог
`cache` (или смонтированный `/app/cache`) можно очистить вручную: это только
кеш, в БД ничего не хранится. После очистки постеры скачаются заново при
следующем открытии списка. `media/` при этом не затрагивается.

## 8. Диагностика

Логи пишутся через `web_logger.log` в `logs/debug.log` / `logs/error.log`.
Ключевые сообщения:

| Сообщение | Что означает |
| --- | --- |
| `Start downloading: <url>, movie_pk: <id>` | загрузка запущена |
| `Downloaded and cached: <url>, movie_pk: <id>` | файл успешно сохранён |
| `Already cached: <url>, movie_pk: <id>` | файл уже был в кеше |
| `Poster already marked as missing: ...` | активен `.missing` |
| `Poster not found, using placeholder instead: ...` | источник отдал `404/410` |
| `Error downloading image (marked as failed): ...` | временная ошибка |
| `Failed to prime fastpic session: ...` | не удалось получить cookie fastpic |

Типовые проверки:

1. **Постер показывает `unavailable`.** Проверить, есть ли рядом с файлом
   `<file>.missing` и какого он размера/возраста. Пустой старый маркер должен
   игнорироваться; если он создан текущей версией и моложе 24 часов — источник
   действительно ответил `404/410`.
2. **Постер долго не появляется.** Проверить `<file>.failed` и `logs/debug.log`.
   Если в логе `Failed to prime fastpic session`, проблема в доступе к
   `https://fastpic.org/`.
3. **Файл есть, но браузер показывает заглушку.** Проверить, что endpoint
   возвращает `200`, а не `302`; убедиться, что список отдаёт внутренний
   `poster_url`. При необходимости сделать hard reload.
4. **В кеш попал HTML.** Проверить первые байты файла (`<!doctype`, `<html`).
   Загрузчик не проверяет `Content-Type` ответа: если источник отдал `200` с
   HTML, он будет сохранён как изображение. Это известное ограничение.

## 9. Ограничения и компромиссы

- **Imgbox и подобные источники.** Ответы `200` намеренно не анализируются по
  содержимому. Если источник вернул картинку-заглушку как успешное изображение,
  она сохранится и будет показана. Это считается ответом источника.
- **Нет проверки `Content-Type`.** Загрузчик доверяет успешному HTTP-ответу.
  `200 text/html` от источника попадёт в кеш как файл с расширением из URL.
- **`.missing` не вечен.** Через 24 часа постер будет запрошен снова. Это
  защита от ложных `404` после смены антибот-политики источника.
- **Клиентские повторы ограничены ~33 секундами.** Если источник недоступен
  дольше, компонент покажет fallback. Новый цикл начнётся при новом `src` или
  повторном создании компонента/перезагрузке страницы.
- **Состояние загрузок — в памяти процесса.** При нескольких worker-ах возможны
  дублирующиеся загрузки. Атомарная публикация делает это безопасным.
- **Cookie fastpic кешируются на процесс.** После рестарта Django они будут
  получены заново. При истечении/инвалидации cookie загрузчик обновит их по
  `403/404`.
- **Приоритеты.** Endpoint кеширует постеры для любого приоритета; ограничение
  `VALID_PRIORITY` осталось только в legacy-хелпере `get_cached_image_url`.
