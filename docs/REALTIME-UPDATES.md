# Live-обновления в UI: polling вместо WebSocket

> **Статус:** архитектурное решение принято (ADR), 2026-11-21.
> Пересматривать только при срабатывании триггеров из раздела 6.
>
> **Коротко:** live-обновления внешних состояний (qBittorrent, Plex, очередь
> TMDB, best-movies) делаются через polling. WebSocket используется только для
> потоковых событий, рождающихся на сервере (логи скана, match-log) — см.
> [`WEBSOCKET-LOGGING.md`](WEBSOCKET-LOGGING.md).

## 1. Контекст

В Vault прогресс раздач обновляется опросом `POST /api/qbittorrent/progress`
каждые 5 секунд (`front/src/routes/(vault)/+page.svelte`). Периодически
возникает идея перевести это на WebSocket.

Ключевой факт: **qBittorrent Web API не имеет push-канала**. Состояние
отдаётся по запросу (`/api/v2/torrents/info`, дельта — `/api/v2/sync/maindata`),
WebUI qBittorrent сам опрашивает сервер. WebSocket не устраняет опрос
qBittorrent, а лишь переносит его внутрь backend и добавляет доставку
снапшота клиенту.

Приложение — single-user, self-hosted, обычно одна активная вкладка.

## 2. Решение

1. Live-обновления внешнего состояния — polling с фронтенда.
2. WebSocket — только для потока событий с сервера (логи, уведомления
   фоновых задач).
3. SSE не вводим: те же издержки, что у WebSocket, а текущая инфраструктура
   (`channels` + `web_logger/pg_bridge.py`) уже закрывает нужный сценарий.

## 3. Обоснование

Стоимость текущего polling в Vault:

- один HTTP-запрос раз в 5 с на видимую вкладку (~720 запросов/час, 1–2 КБ);
- один SQL-запрос (`UserPreferences.get()`) и один локальный вызов qBittorrent;
- в запрос уходят только infohash раздач, видимых на экране (до 200), а не
  весь клиент;
- опрос приостанавливается на скрытой вкладке;
- `progressRequestInFlight` не даёт накапливать параллельные запросы;
- ошибки qBittorrent намеренно не ломают Vault.

Polling здесь уже не «наивный»: он дешёвый, самовосстанавливающийся и
тестируется как обычный endpoint.

Что дал бы WebSocket и чего он стоит:

- **+** латентность ниже 5 с; один запрос к qBittorrent на весь backend.
- **−** REST всё равно нужен для первичного снапшота и fallback — два пути
  поддержки вместо одного;
- **−** состояние на сервере: consumer, группа, подписка/отписка, отдача
  начального состояния при подключении;
- **−** реконнект и рассинхрон (сон ноутбука, half-open сокеты, рестарты
  daphne в dev); polling восстанавливается сам;
- **−** если поллер живёт в HUEY — нужен `web_logger/pg_bridge.py`
  (`InMemoryChannelLayer` не работает между процессами);
- **−** тесты через Channels/`WebsocketCommunicator` вместо обычного API-теста;
- **−** новая поверхность безопасности: `LogConsumer` сейчас не проверяет
  аутентификацию, любой новый consumer надо закрывать;
- **−** сложнее диагностика («почему не пришло?» без явной ошибки).

Выигрыш в латентности для процента на карточке не наблюдаем: 5 с против
мгновенного обновления на значении «62%» глазом не различаются. Порог, где
polling начинает мешать, — десятки клиентов или события частотой ≥1 Гц;
в этом приложении такого нет.

WebSocket уже оправдан там, где он используется: поток логов скана и
match-log. Там события рождаются на сервере часто, построчно, из другого
процесса, и задержка в 5 с убила бы смысл.

## 4. Что это значит для будущих задач

- Не переводить прогресс qBittorrent, статус Plex, очередь TMDB и подобные
  снапшоты внешнего состояния на WebSocket/SSE без срабатывания триггеров
  из раздела 6.
- Новый live-сценарий сначала реализуется polling-ом; WebSocket — только если
  это поток событий, а не периодический снапшот.
- При добавлении WebSocket-канала обязательно: проверка
  `request.user.is_authenticated`, отправка начального состояния и
  реконнект на клиенте.

## 5. Дешёвые улучшения вместо WebSocket

1. Адаптивная частота: 5 с только пока есть активные загрузки
   (`QBT_DOWNLOADING_STATES`), иначе 15–30 с или остановка.
2. Backoff при `available = false` (qBittorrent недоступен): 30–60 с вместо 5 с.
3. Plex: `POLL_MAX_ATTEMPTS = 30` × 2 с = 60 с — длинная синхронизация
   перестаёт обновляться; опрашивать до факта завершения с большим
   предохранителем.
4. Общий хелпер `pollWhile` (видимость, in-flight, backoff, условие остановки)
   вместо четырёх копий логики в `(vault)`, `plex`, `tmdb-sync`, `best-movies`.
5. При росте объёма — перейти на дельту qBittorrent `/sync/maindata` с `rid`;
   это полезнее WebSocket и не требует нового транспорта.

## 6. Когда пересматривать

- Появилось несколько одновременных клиентов (телефон + десктоп + ТВ) и
  polling стал заметен по нагрузке.
- Нужны мгновенные события на всех страницах одновременно (глобальные
  уведомления «торрент докачан», «скан завершён», «ошибка фоновой задачи»).
- Частота обновляемых событий превысила ~1 Гц на клиента.
- Появился внешний источник с настоящим push-каналом.

При наступлении любого пункта — делать **один общий** канал уведомлений,
а не отдельный WebSocket ради прогресс-бара.

## 7. Где это в коде

- `front/src/routes/(vault)/+page.svelte` — polling прогресса (5 с,
  видимость, in-flight guard).
- `front/src/lib/qbittorrent.ts` — типы и `QBT_DOWNLOADING_STATES`.
- `qbittorrent/api.py::progress` — `POST /api/qbittorrent/progress`.
- `qbittorrent/services/torrent_service.py::get_progress` — один вызов
  `torrents_info(torrent_hashes=...)`, ошибки не пробрасываются.
- `front/src/lib/services/scanLogger.svelte.ts`,
  `front/src/routes/match-log/+page.svelte` — легитимное использование
  WebSocket (поток событий).
- `web_logger/websocket_consumers.py`, `web_logger/pg_bridge.py` — текущая
  WebSocket-инфраструктура.
