Да, я бы рекомендовал отказаться от промежуточного `requirements.txt` и перейти на установку зависимостей через `uv` непосредственно во время сборки Docker-образа.

Это не просто косметическое улучшение. Ты сможешь:

- Использовать один источник истины — `uv.lock`.
- Избавиться от генерации и удаления `requirements.txt`.
- Не зависеть от `pip` внутри контейнера.
- Получить воспроизводимую установку зависимостей.
- Сохранить отсутствие dev-зависимостей в production.
- Использовать Docker cache для ускорения повторных сборок.

При этом я бы не отказывался от виртуального окружения внутри контейнера. Даже если контейнер изолирован, `.venv` имеет вполне практические преимущества.

## 1. Как я бы организовал Dockerfile

Для твоего проекта Django я бы использовал стандартную схему `uv sync`.

Пример:

```
FROM python:3.12-slim

# Устанавливаем uv, не используя pip
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app

# Настройки uv
ENV UV_COMPILE_BYTECODE=1
ENV UV_LINK_MODE=copy
ENV UV_NO_DEV=1

# Сначала только файлы зависимостей
COPY pyproject.toml uv.lock ./

# Устанавливаем зависимости, но пока не устанавливаем сам проект
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-install-project

# Копируем исходники
COPY . .

# Завершаем установку проекта
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen

# Используем виртуальное окружение по умолчанию
ENV PATH="/app/.venv/bin:$PATH"

# Дальше твои настройки запуска Django
```

Здесь важны несколько моментов.

`uv sync --frozen`

Использует существующий `uv.lock`, не пытаясь его обновить. Это то, что нужно в production.

`UV_NO_DEV=1`

Исключает dev-группы зависимостей. Аналог твоего `uv export --no-dev`.

`--no-install-project`

На первом этапе устанавливаются только зависимости. Сам проект устанавливается после копирования исходников.

`--mount=type=cache`

Использует кэш uv между Docker-сборками. При изменении исходников, но неизменных зависимостях, Docker не будет повторно скачивать все пакеты.

Это схема непосредственно из официальной документации uv.&#x20;

## 2. Зачем виртуальное окружение внутри контейнера?

Здесь есть два подхода:

| Подход                 | Преимущества                                       |
| ---------------------- | -------------------------------------------------- |
| System Python + pip/uv | Чуть проще, меньше файлов                          |
| `.venv` + uv           | Изоляция, предсказуемость, стандартный workflow uv |

Важный нюанс: контейнерная изоляция действительно делает установку в System Python допустимой. Сама команда uv это поддерживает через `uv sync --system` (или `uv pip install --system`).

Но я всё-таки выбрал бы `.venv`.

Почему:

- Не загрязняешь системный Python.
- Меньше проблем при добавлении системных Python-инструментов.
- Можно переносить окружение между стадиями multi-stage Docker build.
- Не нужно использовать `--system`.
- Запуск приложения не зависит от того, куда установлены глобальные пакеты.

При этом `.venv` не требует активации: достаточно добавить её `bin` в `PATH`.

## 3. Ещё один важный нюанс: `--frozen` или `--locked`?

Я бы использовал `--locked` там, где доступны оба файла `pyproject.toml` и `uv.lock`.

Разница:

- `--frozen` — использует lock-файл как есть, не проверяя его актуальность относительно `pyproject.toml`.
- `--locked` — проверяет, что lock-файл соответствует `pyproject.toml`, и завершает сборку с ошибкой, если это не так.

Для production второй вариант предпочтительнее: не получится случайно собрать образ с устаревшими зависимостями.

Поэтому в приведённом Dockerfile я бы даже заменил оба `--frozen` на `--locked`: оба файла уже скопированы до первой установки.

## 4. Что изменить в твоём Makefile?

Фактически ничего принципиального.

Я бы оставил его примерно таким:

```
build-and-push:
	uv version --frozen --bump patch
	python manage.py collectstatic --noinput
	docker build -t swasher/movie-filter-pro-v2:amd64 . && docker push swasher/movie-filter-pro-v2:amd64
```

Больше не нужны:

```
uv export --no-dev --no-hashes --format requirements-txt > requirements.txt
rm requirements.txt
```

`uv.lock` становится единственным источником зафиксированных версий зависимостей.

Обрати внимание: `uv version --frozen --bump patch` изменяет версию проекта, но не обновляет зависимости. Это нормально.

## 5. Не забудь `.dockerignore`

Обязательно:

```
.venv
__pycache__
.git
.pytest_cache
.mypy_cache
.ruff_cache
*.pyc
```

Особенно `.venv`: локальное Windows-окружение нельзя переносить в Linux-контейнер. uv должен создать его заново внутри Docker.

## 6. Моя итоговая рекомендация

Для твоего Django-проекта я бы выбрал именно эту архитектуру:

1. `uv.lock` — фиксация всех зависимостей.
2. `uv sync` — установка зависимостей в Docker.
3. `.venv` — окружение внутри контейнера.
4. `PATH` — автоматическое использование этого окружения.
5. `UV_NO_DEV=1` — production без dev-зависимостей.
6. Docker cache — повторные сборки без повторной загрузки пакетов.

Две небольшие оговорки:

- В Makefile у тебя стоит `uv version --frozen`. Если этот параметр намеренно не обновляет lock-файл при bump версии проекта, не стоит без проверки переходить на `--locked`: он может обнаружить рассогласование. В таком случае оставь `--frozen` в Docker.
- Если твой Django-проект не оформлен как устанавливаемый Python-пакет, не нужно насильно устанавливать сам проект через `uv sync`. Можно настроить `tool.uv.package = false` и синхронизировать только зависимости.

И ещё: вместо `uv:latest` в Dockerfile лучше зафиксировать конкретную версию uv. Это уменьшит вероятность неожиданных изменений сборки.&#x20;
