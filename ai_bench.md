# gemma-4-26B-A4B-it-qat-GGUF-UD-Q4_K_XL

В приложении реализовано два механизма импорта данных Kinorium: текущий (через веб-интерфейс) и устаревший (через команду Django).
1. Текущий механизм (Web UI)
   Как запускать:
   Перейти на страницу /kinorium/table/ в веб-интерфейсе и загрузить два CSV-файла:
- file_movie_list — списки фильмов (например, "Буду смотреть").
- file_votes — просмотренные фильмы (рейтинги).
  Как реализовано:
- Парсинг: Логика находится в kinorium/parse_csv.py. Парсер ожидает файлы с разделителем \t (tab) и кодировкой UTF-16.
- Логика:
- parse_file_movie_list сопоставляет статусы: "Буду смотреть" $\rightarrow$ WILL_WATCH, "Не буду смотреть" $\rightarrow$ DECLINED.
- parse_file_votes помечает все фильмы как WATCHED.
- Обновление: Реализовано по принципу полной перезаписи: сначала вызывается Kinorium.objects.all().delete(), затем все данные из файла добавляются через bulk_create.
2. Устаревший механизм (CLI)
   Как запускать:
   uv run python manage.py import_kinorium_csv (команда импортирует данные напрямую в таблицы приложения vault, а не в кэш Kinorium).
   Как реализовано:
   Команда vault/management/commands/import_kinorium_csv.py выполняет гораздо более глубокий импорт: фильмы, персоны, жанры, страны, списки пользователя, рейтинги и даже комментарии/заметки.
3. Недочеты и риски
1. Риск потери данных (Критично): Текущий веб-импорт использует схему delete() -> bulk_create(). Если во время вставки произойдет ошибка (например, прервется соединение или файл окажется битым), старые данные уже удалены, а новые не записаны. Таблица останется пустой.
2. Отсутствие транзакционности: Операции удаления и вставки не обернуты в transaction.atomic.
3. Блокировка запроса: Весь процесс парсинга и записи происходит в рамках одного HTTP-запроса. При больших файлах это может привести к таймауту сервера или зависанию интерфейса.
4. Жесткая привязка к кодировке: Ожидается только UTF-16. Любое другое кодирование приведет к ошибке.
5. Потребление памяти: Весь файл считывается в память целиком (file.read()), что может вызвать Out of Memory на больших объемах данных.
4. Рекомендации по улучшению
- Использовать транзакции: Обернуть delete и bulk_create в transaction.atomic, чтобы гарантировать целостность данных.
- Перейти к инкрементальному обновлению (Sync): Вместо удаления всего содержимого использовать логику сравнения (Upsert). Это позволит не терять данные при сбоях.
- Асинхронность: Вынести импорт в фоновую задачу (например, Celery или Django Q), чтобы пользователь не ждал завершения запроса, а видел прогресс.
- Валидация перед действием: Сначала проверять структуру и кодировку файла, и только если файл корректен — начинать работу с базой данных.
- Удалить legacy-код: Если import_kinorium_csv больше не нужен (как указано в документации), его следует удалить, чтобы не вводить в заблуждение.
